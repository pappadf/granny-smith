# Predecoded interpreter cores

The 68K and PowerPC cores each have two executors behind one entry point
(`cpu_run_68000/68030/68040`, `ppc_run`): the original big-switch decoder
(`cpu_run_*_switch`, the `while` loop in `ppc_run`) and the **predecoded
executor** this document describes.  `predecode.enabled` selects between
them at run time (default 1, with `predecode.elide` at 2); both are always
built, and the switch cores remain the reference the differential rows
compare against.  Source:
`src/core/cpu/predecode.[ch]` (the shared page cache), `cpu_pd_run.h` /
`cpu_pd_classify.h` / `cpu_pd_ids.h` (68K), `ppc/ppc_pd_run.h` /
`ppc_pd_classify.h` / `ppc_pd_ids.h` (PowerPC), `scripts/gen_pd_cases.py`
(the generated T1 id tables under `build/gen/`).  The design and its
measurements are in the completed proposal
`local/gs-docs/proposals/completed/proposal-predecoded-interpreter-cores.md`.

## What it is

A **decode cache keyed by host page**.  The switch executor decodes every
instruction on every execution: fetch, mask, index a decode tree, and then
resolve the effective address from the raw bits.  The predecoded executor
instead keeps, for every 4 KB guest page that has executed, one entry per
possible instruction start (2048 for the 68K's 16-bit words, 1024 for the
PowerPC's 32-bit words) holding the decoded shape:

```c
typedef struct pd_entry {
    uint16_t id; // handler id: control (0..15), T1 (flat leaf), or T0 (specialized shape)
    uint8_t a, b; // register byte offsets, condition, size — per shape
    uint32_t c; // immediate, displacement, in-page target index, absolute target, or the raw word
} pd_entry_t; // 8 bytes
```

Entries decode **lazily**: a block starts all-`PD_UNDECODED`, and the loop
decodes an entry the first time execution reaches it.  A block also holds a
raw shadow of the page's words (`raw16[]` / `raw32[]`), so an entry is
always consistent with the words it was decoded from and the debug build
can audit that.

It is **not** a JIT and not a basic-block cache: there is no generated
code, no block boundaries, no chaining.  Every instruction still runs a C
handler; what the cache removes is the decode and the effective-address
resolution, and it turns the fetch into an array index.

### Tiers

| Tier | Id range | Meaning |
|---|---|---|
| control | 0..15 | `PD_UNDECODED` (decode on first execution), `PD_CROSS` (the instruction straddles the page end), `PD_GENERIC` (a shape the predecoded path never handles: FPU, MMU, the model-specific leaves) — the last two run one instruction through the switch-core step and look again |
| **T1** | 16..`T1_END` | one id per leaf of the decode tree (`cpu_decode.h` / `ppc_decode.h`), generated by `gen_pd_cases.py`.  The entry carries the raw word(s); the handler is the core's own `OP_` body, so a T1 instruction is decode-free but otherwise identical to the switch core |
| **T0** | `T1_END`.. | specialized shapes (`cpu_pd_ids.h`'s `PD_FAMILIES`, `ppc_pd_ids.h`'s `PPC_PD_T0`): the entry carries the operand offsets and immediates the handler needs, so the body is a few loads and stores.  68K families come in shape slots (`PD_ID_S7P`: seven source EA modes; `D6P`: six destination modes; `S7S`) plus flag-liveness twins (see Elision) |

The 68K's T1 leaves and the PowerPC's are generated from the trees, so a
new leaf in either tree gets a T1 id (and a `case`) without editing the
predecoded core.  A T0 shape is a hand-written classifier rule + handler;
`predecode.hist` prints which ids decode most, which is how the T0 sets
were ordered (`docs/notes/predecode-shape-histograms-2026-09-01.md`).

### The loop

`cpu_pd_run_<model>` / `ppc_pd_run` keep the sprint ABI exactly:
`*instructions` is the burn-down counter the memory layer writes through
(`g_bus_error_instr_ptr`, I/O penalties), decremented after every retired
instruction, saturating; the PowerPC loop folds branches into their
successor on the same rule as the switch loop (never on the last slot).
The sprint prologue/epilogue (trace, halt, interrupt poll, the PowerPC
machine-check delivery) are the switch core's.  Inside the sprint the
loop holds the current block, the cursor into it and the page's guest
address; `p->pc` / `cpu->pc` are **materialized** only at the exits and
wherever a handler may observe them (exceptions, the interrupt poll, the
generic step).  Anything that can leave the page (`PD_CROSS`, branches
out, exceptions, a `PD_GENERIC` step) goes through `relookup`, which
finds the target block through the active read table (68K) or the fetch
window (PowerPC — refilled right there on a transition, so a page change
costs an ftlb hit and a pool lookup, not a generic step) and continues;
pages without a host mapping (device windows), logpointed pages and
demoted pages run through the generic step one instruction at a time,
re-trying the lookup after each step unless the pool declined the page.

### What the loop cannot see

The invariants that keep the two executors byte-identical (the
differential checkpoints under `tests/integration/predecode-diff/`, and
at instruction granularity the `m68k_vectors` and `ppc_vectors` unit
suites, which replay the m68k-test / powerpc-test conformance vectors
with unlisted state randomized — `m68k_vectors` runs every vector
through both executors and fails on any difference):

- **Model epilogues are shared.**  `PD_ENTER` latches the 68000's `ir`
  for the illegal-instruction path, arms the `_sp0` audit, and runs the
  same trace/halt/stopped tests as the switch core.
- **Exceptions inside a handler set `pc` before they raise**, exactly as
  in the switch core (`instruction_pc` is set for every entry that can
  fault: `PD_P_CANFAULT`).
- **The last slot never folds** (PowerPC) and **never elides** (68K): the
  instruction that ends a sprint is the one single-step, breakpoints and
  logpoints see.

## Coherence

The cache is valid as long as the page's words are what the block was
decoded from.  The memory layer guarantees that with **code-page marks**
(`docs/core/memory/memory.md`, "Code-Page Coherence"): when a block is
allocated the page is marked, marking zeroes the page's SoA write entries
in every table, and every refill site plants write entries only through
`memory_write_fill()`, which declines on a marked page.  Guest stores to
code therefore take the slow path, which calls `memory_host_written()`,
which invalidates the block (`predecode_invalidate_host`).  Direct host
writers (DMA, checkpoint restore, `memory.write`) call the same hook.

Consequences the executor relies on:

- a store from *within* the current block invalidates it; the loop
  checks the block's generation and the page's entry state at every
  redispatch, so it never runs a stale entry;
- a page that keeps being written (a stack that briefly held code, a
  data page a handler jumped through, a system-heap page that mixes
  patches with the structures they work on) **demotes**.  The rule is
  economic: a suppressed store costs roughly `thrash_ratio` instructions'
  worth of predecode gain, so once a page took more than `thrash_limit`
  stores within a window of `thrash_window` page transitions AND those
  stores times the ratio exceed the instructions the page retired in the
  window (the executors charge retired instructions to a block at every
  block exit, `predecode_enter`), the page goes back to the generic tier
  for `demote_hold` page transitions and its write entries come back
  (`predecode.demotions`).  A hot loop that stores into its own page is
  therefore kept; a data page a handler occasionally runs through is
  dropped quickly;
- `memory_map_init` bumps `g_mem_map_generation`; the pool resets lazily
  on the next lookup, so a rebooted machine never sees blocks of the old
  image;
- a block is keyed by host page but **decoded at one guest address**:
  PC-relative operands and out-of-page branch targets are stored as
  absolute addresses, so when the same host page executes through another
  alias (the AV's ROM overlay at zero, a 24-bit mirror, a second BAT
  mapping) the lookup re-decodes the block for that alias
  (`predecode.realiases`).

The **debug build** (`GS_DEBUG`) audits every T0/T1 dispatch against the
raw shadow (`PD_AUDIT_68K` / `PD_AUDIT_PPC`) and traps on the first
stale entry; the release loop has no such check.

## Elision (68K)

Most 68K instructions write the condition codes, and most of those writes
are dead: the next flag-writing instruction overwrites them before any
conditional reads them.  `predecode.elide` selects how far the executor
exploits that:

| Level | Rule |
|---|---|
| 0 | none: every handler writes the flags the hardware writes |
| 1 | **E1** — an entry whose flags are dead *within the same page*, with the next flag-writing instruction provably reached, dispatches to its **twin** id (`id+1`, the no-flags body).  Only shapes marked `PD_P_ELIDABLE` (write all of NZVC, cannot fault, cannot trap) |
| 2 | **E2** — E1, plus elision across an instruction that *can* fault when the block has seen no slow-path access since it was decoded (`g_mem_slowpath_count` guard); a fault or a device access re-decodes at level 1 |

Exactness rules that make the elided run byte-identical to the switch
core, including at every checkpoint:

- the analysis is per entry and per block, redone on every (re)decode;
- the **last slot** of a sprint dispatches the full-flags id
  (`redispatch` steps the twin id back by one), so `sr` is exact at every
  sprint boundary — and therefore in every checkpoint, single step,
  breakpoint and logpoint;
- an exception, trace, or interrupt materializes through the same slot
  rule, so the handler that runs next sees hardware flags;
- a shape whose flag result depends on a memory operand that could fault
  is only elided at level 2, and level 2 falls back to level 1 semantics
  the moment the page takes a slow-path access.

The PowerPC executor has no elision: `Rc`/`OE` forms are separate ids and
CR writes are cheap.

## Object surface

```
predecode.enabled           RW  select the executor (also machine.cpu.predecode)
predecode.elide             RW  0 / 1 / 2 (68K only)
predecode.pool_cap          RW  blocks in the pool (default 2048)
predecode.thrash_limit      RW  suppressed stores per window before the ratio rule applies (32)
predecode.thrash_window     RW  the window, in pool lookups (4096)
predecode.thrash_ratio      RW  stores x ratio > instructions retired in the window (64)
predecode.demote_hold       RW  page transitions a demoted page stays on the generic tier (65536)
predecode.blocks / lookups / allocs / evictions / decodes / invalidations /
predecode.demotions / elided / suppressed_writes                                   RO
predecode.generic_steps (+ generic_cross / generic_declined / generic_slowmode)    RO
predecode.relookup_nomap / relookup_nopool (+ lookup_noregion / lookup_held)      RO

The generic-tier counters are the tuning view: `generic_steps` is every
instruction that ran through the one-instruction step executor, split by
cause (a page-straddling entry, a declined shape, the executor's own slow
mode), and the relookup counters say why a page transition found no
block (no fast-path read entry yet, or the pool declined: no code region,
or demoted and held).
predecode.hist [top]        print the most-decoded ids with names (68K and PPC)
predecode.reset             drop every block (the next lookup re-decodes)
```

Tests: `tests/unit/suites/cpu_predecode` (allocation, eviction, coherence,
elision, the `PD_BENCH=1` loop microbenchmark), `memory_codepage`
(marks and refill sites), and every CPU suite with `CPU_TEST_PREDECODE=1`
(`CPU_TEST_ELIDE=<level>`) — CI runs the conformance vectors both ways.
The differential runs (`make integration-test-predecode-diff`) boot the
Plus, the IIcx and the 6100 both ways and compare checkpoints byte for
byte.

## Adding a shape

1. Add the family to `PD_FAMILIES` (68K) or `PPC_PD_T0` (PowerPC) with
   its shape slot count and property bits.
2. Teach the classifier (`cpu_pd_classify.h` / `ppc_pd_classify.h`) to
   emit it: override the tree's `OP_` name, decline (return the T1 id)
   whenever the operands are not what the handler assumes — the A7 byte
   post-increment, an unaligned target, an OE form.
3. Write the handler with the `PD_CASE` / `PPD_CASE` macros; for an
   elidable 68K shape write the body once and let `PD_PAIR` stamp the
   twin.
4. Run the CPU suite both ways and the differential rows.  A T0 handler
   is correct when nothing observes the difference.
