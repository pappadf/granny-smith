# Power Macintosh 9500/180MP

The Power Macintosh 9500/180MP is the 9500 board with Apple's two-way processor card: two
PowerPC 604e processors at 180 MHz on one plug-in card, sharing the 60x bus under Hammerhead
arbitration. Apple's own comparison places it as the predecessor of the 9600/200MP, which
differs from it in "Clock speed 200 MHz, dual PPC604e microprocessors" plus the 9600's
enclosure, CD-ROM and display-card changes [1] Table 1-1 p. 2. Everything below the processor
card is the 9500's ([pm9500.md](pm9500.md)); the card's register surface is Hammerhead's three
multiprocessor registers ([hammerhead.md](hammerhead.md) §2.5–§2.7) plus two reused addresses
([pm9600.md](pm9600.md) §4.5). This page records what the 9500's page and the 9600's page do
not: how the card's surface behaves as the shipping firmware and the operating systems that
drive it actually use it.

## 1. Identity

The machine is indistinguishable from a uniprocessor 9500 by every identity mechanism the
platform has — Hammerhead's identifier and machine-class flag, BoxID, the 68k product record
and gestalt 67, the Open Firmware root `AAPL,9500` (pm9500.md §1.2; tnt.md §2.6) — because
the identity lives on the main logic board and the board is the 9500's. Software learns that
a second processor exists only by reading Hammerhead `ArbConfig` and finding bit `$02`
(`TwoCPU`) set ([hammerhead.md](hammerhead.md) §2.5; [3]).

| Parameter | Value |
|---|---|
| Processors | two PowerPC 604e at 180 MHz on one processor card [1] Table 1-1 p. 2 |
| Processor (AR) bus | not stated by a document in evidence; 45 MHz is the 4:1 reading of the 180 MHz clock (*inferred*, §6) |
| Everything else | the 9500's (pm9500.md §1.3) |

## 2. Deltas vs the family doc

The single delta against the 9500 is the processor card; against the family doc it is the
9500's deltas (pm9500.md §2) plus the card. No board register, decode or interrupt line
changes: the card's surface is three Hammerhead registers that exist on every TNT board and
read their uniprocessor values there ([hammerhead.md](hammerhead.md) §2.5–§2.7), the start
mailbox aliased on Bandit 1's configuration-address latch, and the Ethernet-PROM chip select
inside Grand Central's window ([pm9600.md](pm9600.md) §4.5).

## 3. Per-subsystem wiring: the two-way card

### 3.1 The register surface

| Address | Name | Access | Behaviour | Witness |
|---|---|---|---|---|
| `$F8000090` | `ArbConfig` | read byte | bit `$02` `TwoCPU` set on this machine; the boot ROM read-modify-writes the register during hardware initialization and the bit survives | [3], [5] (*observed*) |
| `$F80000B0` | `WhoAmI` | read byte | `$10` to the primary, `$08` to the secondary — a function of the processor issuing the load | [3], [6] |
| `$F80000C0` | `IntReg` | byte latch | bit `$80` `SecInt`, active low: written clear, the secondary is signalled; written set, the signal is withdrawn. Reads return the latch | [3], [4], [6] |
| `$F2800000` | Bandit 1 configuration-address port | write u32 | the secondary's start vector, as a big-endian physical address | [3], [4], [6] |
| `$F3019000` | Ethernet PROM chip select | read | an access by the **secondary** interrupts the primary on Grand Central source 30 | [2] §4.2, [4], [6] |

### 3.2 The secondary's lifecycle: parked, called, running

The three consumers in evidence — the boot ROM's Open Firmware, Linux and BeOS — agree on one
contract (*inferred* from their combined use; no Apple document describes it):

1. **Parked.** After reset the secondary executes nothing visible to software: the ROM's
   68k and NanoKernel halves contain no multiprocessor code ([pm9600.md](pm9600.md) §3.8), and
   the secondary takes no part in hardware initialization.
2. **Called.** A write to `IntReg` with `SecInt` clear, while the secondary is parked, starts
   it at the address held in the `$F2800000` mailbox, with translation off — and with a
   return path: an entry routine that ends in `blr` brings the processor back to rest (§3.3).
3. **Running.** Once it has not returned, the secondary is an ordinary processor, and `SecInt`
   is its interrupt input: asserted (bit clear) it interrupts the secondary, released (bit
   set) it does not. The secondary receives no other interrupt — Grand Central's output goes
   to the primary alone (tnt.md §5).

The trigger is the **write**, not a 1-to-0 transition of the bit: Open Firmware leaves
`IntReg` at `$00` (§3.3), and BeOS's start sequence then writes `$00` over it (§3.4) and
expects the secondary to start. Linux's driver, which pulses the bit and afterwards rewrites
the mailbox to `$100` "so if we get another intr we won't try to startup again" [4], is
consistent with the same contract.

### 3.3 Open Firmware's use of the card

The firmware's construction of the `/chosen` node reads `ArbConfig` and `IntReg`
([hammerhead.md](hammerhead.md) §2.5, §2.7). With `TwoCPU` set it writes `$00408B38` to the
`$F2800000` mailbox and then `$00` to `IntReg` (*observed* on the 1995 ROM, [5]). Physical
`$00408B38` holds, at that moment, a three-instruction routine from the firmware's own image:

```
mfspr  r0,pvr        ; the processor version register
stw    r0,12(r1)     ; stored at r1+12
blr                  ; return
```

Entered with the registers a hard reset leaves at zero, the secondary stores its PVR at
physical `$0000000C` and returns. This is how the firmware can learn the second processor's
version, and it presupposes the return path of §3.2 step 2: a `blr` through a zero link
register would otherwise run the processor into low memory. Firmware-level multiprocessor
code is therefore present — in Open Firmware, not in the ROM's other components.

### 3.4 BeOS's use of the card

BeOS 5.0.3's kernel ([beos.md](../../os/beos.md) §5.7) starts the secondary as follows [6]:

1. reads `ArbConfig` and requires `TwoCPU`;
2. writes the physical address of its secondary entry (`$000568AC` in the 5.0.3 kernel) to
   `$F2800000`;
3. signals with an atomic AND of `IntReg` with `$7FFFFFFF` (`lwarx`/`stwcx.`) — clearing
   `SecInt`;
4. polls `IntReg` until bit `$80` reads set, with a delay between reads.

The secondary's entry code runs with translation off, clears MSR[IP], sets up HID0, loads its
stack from low memory, reads `WhoAmI` to learn its processor number (`$10` → 0, otherwise 1),
and acknowledges with an atomic OR of `$80000000` into `IntReg` — the bit the primary is
polling. Interprocessor interrupts thereafter use the same two paths: to the secondary, the
AND that clears `SecInt`, withdrawn by the secondary's own OR; to the primary, a byte read of
`$F3019000`, cleared by writing bit 30 to Grand Central's interrupt Clear register and
re-reading until the bit drops. Both processors then run the kernel symmetrically; device
interrupts are taken on the primary only.

### 3.5 Which processor's PROM access rings

The primary reads the Ethernet PROM for the station address — the BeOS bootstrap reads the six
address bytes at `$F3019000 + $10·n` and compares them with Open Firmware's
`local-mac-address`, before any kernel is loaded [6]. That bootstrap's interrupt poll treats a
pending Grand Central source 30 on this platform as an interprocessor interrupt and has no
handler that clears it; a source-30 event raised by the primary's own reads would leave it
polling forever. Every sender of the primary's interrupt in evidence is the secondary (Linux's
message pass to processor 0 [4], BeOS's `interrupt_cpu(0)` [6]), and the derived server
design describes the path as "the programmatic way for a second processor to interrupt the
first processor" [2] §4.2. The chip select therefore raises source 30 on the secondary's
accesses only (*inferred*, §6).

## 4. Expansion

The 9500's (pm9500.md §4). The two-way card occupies the processor-card slot.

## 5. Boot sequence summary

The 9500's (pm9500.md §5), with one addition: during `/chosen` construction Open Firmware
calls the secondary once to read its PVR and lets it return to rest (§3.3). The primary alone
then runs POST's remainder, Open Firmware and Mac OS. The secondary stays parked until an
operating system or multiprocessing library calls it (§3.2).

## 6. Open questions

1. **The card hardware.** Clocks, bus loading, the bus ratio (45 MHz is inference), and how
   the card holds and releases the secondary are described by no document in evidence.
2. **The return path.** Where a called secondary's `blr` lands — a card-provided trampoline,
   or the hard-reset link register value with a parking loop the card supplies — is inferred
   from Open Firmware's routine, not documented.
3. **The 604e identity under the 1995 ROM.** Whether the 1995 firmware recognises the 604e's
   PVR (`$0009xxxx`) when building its `cpu` node, or the 180MP shipped with a later image, is
   not established.
4. **The PROM-select gating.** Whether the chip select rings on the secondary's bus
   transactions only (as §3.5 infers) or on any master's access with the firmware arranging
   never to read it, is not established.
5. **The time-base freeze.** Linux's kick relies on both time bases freezing across the start
   window and restarting on the next `SecInt` ([pm9600.md](pm9600.md) §4.5); what gates the
   604e's TBE inputs on this card is unknown. BeOS does not depend on it: it zeroes both time
   bases at a synchronisation point of its own.
6. **The PVR store at `$0000000C`.** Whether the firmware reads the stored PVR back (and what
   it publishes from it) is not established; the device tree carries a single `cpu` node.
