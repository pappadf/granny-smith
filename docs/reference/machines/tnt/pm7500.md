# Power Macintosh 7500/100

The Power Macintosh 7500/100 is the compact-desktop member of the TNT platform: a 100 MHz PowerPC 601 supplied on the family's replaceable processor card, eight DIMM slots, the Control/Chaos onboard video subsystem with 2 MB of VRAM and video input but no video-output encoder, and — the machine's defining structural property — exactly **one** Bandit PCI bridge, whose single 33 MHz bus serves the three PCI sockets, the DAV connector and the whole Grand Central I/O stack alike. "The Power Macintosh 7500 is the smallest of the new models. It has a compact desktop case with room for expansion cards" [1] §"Features of the Power Macintosh 7500" p. 6, and it is the baseline column of the family's comparison table [1] Table 1-3 p. 5 ([tnt.md](tnt.md) §6.1).

Everything this machine shares with the 7500's siblings — the ASIC set, the memory map, the interrupt, bus and clock architecture, the boot ROM image, the DBDMA engine — is documented once in the family doc and cited here by section, never restated. This page carries only what is unique to the 7500.

## 1. Identity

### 1.1 What the machine is

The 7500 is the one-Bandit, one-processor, 601-powered box of the four machines the August 1995 ROM serves ([tnt.md](tnt.md) §1.2). Its enclosure is a compact desktop with a hinged top chassis that folds out on a support foot and is held open by a stabilizing arm, giving access to the expansion features [1] p. 7. Its position in the family's table of models is the leftmost comparison column: processor PowerPC 601 at 100 MHz, processor upgrade by card, optional L2 of 256 KB–4 MB, eight RAM slots, 2–4 MB of VRAM, built-in 24 bpp video input, no video output, three PCI slots plus a DAV connector [1] Table 1-3 p. 5.

The machine runs the family's single 4 MB mask ROM in either of its two August 1995 releases (header checksums `$96CD923D` and `$9630C68B`); the two releases differ only in the `HWInit`/POST and `Mac68KROM` components ([tnt.md](tnt.md) §1.3). No Apple document states which release a given 7500 shipped with (§6.1).

Because the ROM identifies the machine from hardware at every boot rather than from a name plate, the machine's identity *is* the set of register values its board presents — the subject of the next section.

Two consequences of this column are worth stating. First, the 7500 is the machine the two decodes *separate in opposite ways*: the 68k routine distinguishes it from the 8500 by BoxID bit 11 being clear, while Open Firmware distinguishes it by bit 13 being set ([hammerhead.md](hammerhead.md) §4.3) — a board that gets one bit right and the other wrong yields a machine whose 68k half and native half disagree about which box they are. Second, BoxID's remaining bits (the strap field, the MESH-present and pull-up bits) are not consumed by either decode on this path; their meanings are only community-attested ([tnt.md](tnt.md) §7 item 4, and §6.6 below).

### 2.3 The processor card and the upgrade path

"The main processor and its associated clock circuits are on a plug-in card. The processor card provides an upgrade path to a faster or more powerful microprocessor" [1] §"Main Processor" p. 14 — and the 7500's own feature list names the intended destination: "The processor subsystem is on a replaceable card for easy upgrading to a PowerPC 604 microprocessor or coprocessor" [1] p. 8. The family-level consequences — the bus clock being a property of the card, and the ROM being unable to assume which PowerPC it is running on — are [tnt.md](tnt.md) §2.2's.

The 7500's card as shipped is the 100 MHz 601 with a 50 MHz system bus, i.e. a 2:1 core-to-bus part [1] pp. 6, 17. Because the card, not the board, generates the system clock, an owner's card swap changes the `bus-frequency` the firmware publishes ([tnt.md](tnt.md) §2.2, §7 item 12); nothing in the developer note constrains which cards the 7500's socket accepts beyond the advertised 604 upgrade (§6.11).

Two properties of the card matter to software and are therefore worth pinning here. The ROM reads the processor's PVR at every boot — the Open Firmware identity folds a not-a-601 flag out of it, clear on this machine ([hammerhead.md](hammerhead.md) §4.3) — and the 68k half runs its CPU-identification dispatch before the Toolbox comes up ([tnt.md](tnt.md) §2.2). A card carrying a different processor therefore boots the same ROM through a different dispatch arm without any board change.

## 3. Per-subsystem wiring

### 3.1 The PowerPC 601 as fitted

The 601 as Apple describes it for this machine: "full RISC processing architecture", "parallel processing units: one integer unit and one floating-point unit", "a branch manager that can usually implement branches by reloading the incoming instruction queue without using any processing time", "an internal memory management unit (MMU)", and "a single built-in 32 KB cache for data and instructions" [1] §"PowerPC 601 Microprocessor" p. 14.

Three consequences of that column are unique to this machine within the family:

- **The unified cache.** Because the 601 has one cache for instructions and data, the split-cache coherency problem Apple warns 604 applications about — self-modifying code that bypasses the Code Fragment Manager — does not arise here [1] §"Code Fragments and Cache Coherency" p. 12. Software written to the 601's single-cache model runs as written on this machine.
- **POWER instructions execute natively.** The 601's instruction set "includes some of the same instructions found in the instruction set of the POWER processor" [1] p. 12; on this machine those instructions are real hardware, not the 604's software emulation ("POWER emulation... a more appropriate name for this feature is PowerPC 601 compatibility" [1] §"Emulation for Compatibility" p. 12). Native code for this machine may legitimately contain POWER-only instructions.
- **The L2 timing path.** The cache controller's early-data tricks are documented for both family processors, and the 601's differs: with a single processor "there is only one snooping mode so the ARTRY (address retry) signal is never asserted for a microprocessor access that hits in the L2 cache"; the DBDIS-based same-cycle data drive is a PowerPC 604 facility; and "with the PowerPC 601, data is made available as early as the second clock cycle after the assertion of TS" [1] §"L2 Cache Operation" p. 45. The L2 controller's register surface and organization are [hammerhead.md](hammerhead.md) §3.4–§3.5's.

On the memory side, the 601 also fixes the interleaved read order: Hammerhead's 128-bit interleaved transfers honour "the critical quad-word first behavior of the PowerPC 601" (against the critical-doubleword behavior of the 603/604) [2] §"Data Interleaving" p. 10 — the first data beat of an interleaved read on this machine is the critical quadword, and a memory model that replays the 8500's doubleword ordering mis-serves the first beat of every burst.

### 3.2 Main memory: banks, pairs and sizing

The memory contract — 8-byte (64-bit) DIMMs, the 128-bit interleaved pair, contiguity manufactured by Hammerhead's bank base registers, 15.6 µs CAS-before-RAS refresh, the 1.5 GB controller ceiling — is [tnt.md](tnt.md) §2.3's and [hammerhead.md](hammerhead.md) §3.2's. This machine's population rules:

- **Eight slots, paired by label.** The slots are labelled A1–A4 and B1–B4; "slots with the same number constitute a slot pair" — A1 with B1, A2 with B2, and so on [1] §"Installing RAM DIMMs" p. 36.
- **One DIMM boots.** "The Power Macintosh 7500 and 8500 computers do not have any main memory soldered to the logic board. At least one RAM DIMM must be present for the computer to operate" [1] p. 36 (IMPORTANT note). DIMMs "can be installed one or more at a time" [1] p. 36.
- **A pair interleaves only when matched twice over.** "When the startup software detects two DIMMs that are the same size and type and installed in corresponding slots, it configures them as a single 128-bit-wide data bus" [1] p. 36 — same size *and* same addressing mode, i.e. the pair must use the same address multiplexing [1] pp. 16, 36, §"RAM Address Multiplexing" p. 41. A mixed pair still works, as two 64-bit banks.
- **Bank and DIMM limits.** Minimum bank 4 MB, maximum bank 64 MB, largest DIMM a two-bank 128 MB module [1] §"RAM DIMM Configurations" p. 41. The controller supports 1, 4, 16 and 64 Mbit devices with an access time (T_RAS) of 70 ns or less [1] §"DRAM Devices" p. 43.
- **The 1 GB ceiling and how it is reached.** Eight slots "can provide 1 GB of memory if fully populated with DIMMs that use 64-megabit devices" [1] §"Random-Access Memory" p. 16 — four pairs of 128 MB DIMMs per the configuration table:

| DRAM device size | DIMM configuration | DIMM size | Maximum with 8 DIMMs [1] Table 4-3 p. 41 |
|---|---|---|---|
| 4 Mbit | 512 Kbits by 64 | 4 MB | 32 MB |
| 4 Mbit | 1 Mbit by 64 | 8 MB | 64 MB |
| 16 Mbit | 1 Mbit by 64 | 8 MB | 64 MB |
| 16 Mbit | 2 Mbits by 64 | 16 MB | 128 MB |
| 16 Mbit | 4 Mbits by 64 | 32 MB | 256 MB |
| 64 Mbit | 4 Mbits by 64 | 32 MB | 256 MB |
| 64 Mbit | 8 Mbits by 64 | 64 MB | 512 MB |
| 64 Mbit | 16 Mbits by 64 | 128 MB | 1 GB |

- **Module constraints.** The 8-byte DIMM is the JEDEC MO-161 mechanical / 21-C electrical standard; the connector is a Burndy ELF168E5GC-3Z50 or equivalent; of MO-161's three module heights "the computers accept only the shorter two", maximum height 1.255 inches [1] §"RAM DIMMs" p. 36, §"RAM DIMM Dimensions" p. 43. Load limits: at most two DRAM devices per data line and eight per `/RAS` line on each DIMM [1] p. 43 (IMPORTANT). The connector carries a 12-bit multiplexed address bus, and "the memory controller does not support devices that require more than 12 row address bits" [1] §"RAM Address Multiplexing" p. 41.
- **How sizes are found.** "The system software initializes the address mode bits in the bank base registers as part of the process of determining the amount of RAM installed" [1] p. 41 — sizing is a startup-software activity over Hammerhead's bank base register file ([hammerhead.md](hammerhead.md) §2.10); the slots' presence-detect pins are not used for it ([hammerhead.md](hammerhead.md) §3.2).

### 3.3 The L2 cache as fitted

The 7500's cache SIMM slot is fitted but empty as shipped — "Size of second-level cache: Optional, 256 KB–4 MB" [1] Table 1-3 p. 5, against the 8500's factory 256 KB SIMM. The cache part itself is family-level ([tnt.md](tnt.md) §2.3): a write-back, direct-mapped, allocate-on-read-or-write cache with a synchronous-burst-SRAM data store (access time 11 ns or less) and a standard-SRAM tag store [1] §"Second-Level Cache SIMM" p. 45.

The machine-relevant facts are the sensing path and its boot consequence:

- **Sizes and strap codes.** The SIMM may hold 256 KB, 512 KB, 1 MB or 4 MB [1] p. 45; the connector's `CacheSize(1:0)` lines encode `b00` = 512 KB, `b01` = 256 KB, `b10` = 1 MB, `b11` = 4 MB [1] Table 4-7 p. 49 — the codes the firmware's size read decodes ([hammerhead.md](hammerhead.md) §2.8, §4.4).
- **Sensing.** "The Hammerhead memory controller IC interrogates two pins of this connector during system startup, to determine the size of the memory on the SIMM. If no SIMM is installed, pull-up resistors on these pins cause the Hammerhead IC to disable all external cache operations" [1] §"Second-Level Cache" p. 17.
- **The boot's behaviour without a SIMM.** The firmware's `.L2DataCacheTest` reads Hammerhead `+$E0`, and "if clear, skips the entire test — this is the no-SIMM case" ([hammerhead.md](hammerhead.md) §4.4). On a factory 7500 the POST therefore performs no cache walk and the device tree's `l2-cache` node reflects the absent cache; an owner-installed SIMM enables the fill/flush test and the `+$70` enable word ([hammerhead.md](hammerhead.md) §4.4).

### 3.4 Video: the framebuffer as fitted

The video subsystem's architecture — Chaos bridging the display bus, Control providing addressing and control, RaDACal converting and generating video timing, the 64-bit path into the VRAM and the 128-bit path out to the DAC — is [tnt.md](tnt.md) §2.4's; the bridge's register behaviour, including the fenced configuration space and the firmware's BAR assignment for Control, is [bandit.md](bandit.md) §3.10's. What belongs to this machine:

- **Capacity and what it buys.** The frame buffer is four VRAM slots each taking a 1 MB SIMM [1] §"Video Frame Buffer" p. 20. As shipped, two SIMMs are installed: "The built-in video interface has 2 MB of VRAM, which provides up to 24 bpp on a 17-inch monitor and 16 bpp on a 21-inch monitor" [1] p. 8. Four SIMMs (4 MB) "provide up to 24 bpp on a 21-inch monitor" [1] p. 8. There is no second video stream on this machine, so the family's dual-stream VRAM budgeting ([tnt.md](tnt.md) §2.4) never applies: the whole framebuffer serves the monitor.
- **A monitor is required.** "The Power Macintosh 7500 and 8500 computers require an external video monitor for their graphics displays" [1] §"Video Monitor Connector" p. 29 — unlike a PCI-card machine, there is no configuration in which this box drives no display.
- **The monitor connector and sense system.** The connector is DB-15 with the standard Apple sense lines [1] Table 3-5 p. 29; the machine identifies the monitor "using the Apple monitor sense codes and the extended sense codes" [1] p. 30, supporting 12-inch RGB, 14-inch RGB, 15/17/20-inch multiple scan, VGA, SVGA and 16-inch RGB monitors [1] Table 3-6 p. 30. VGA and SVGA share a sense code: the first startup with an SVGA monitor shows 640×480, and the user's Monitors control panel switch to 800×600 persists across restarts [1] p. 30 note.
- **The interrupt line.** Control's vertical-blanking interrupt is collected by Grand Central on external source **26** on this machine — the shipping video driver toggles mask bit 26 to enable and disable it ([grand-central.md](grand-central.md) §3.2; *observed*, [3]). Note that the tree the ROM builds still publishes the display node's `AAPL,interrupts` as 30, the Platinum wiring ([grand-central.md](grand-central.md) §3.2) — a discrepancy a guest-visible model must reproduce rather than reconcile (§6.4).
- **The boot's mode set, as observed.** The ROM's native Control driver performs the first mode set early in the Mac OS start-up ([tnt.md](tnt.md) §2.7) and programs a 640×480, 32 bpp mode — `mode` register 1, the greater-than-2 MB depth pair — with pitch 2592 (640×4 bytes plus a 32-byte row margin) and `start_addr` `$200`, after which the Display Manager publishes `ScrnBase = $90800210`: the `$90000000` VRAM base plus the `$800000` usable-window offset, plus `start_addr`, plus the 16-byte pixel-0 offset (*observed*, [3]; the BAR assignment is [bandit.md](bandit.md) §3.10's). A depth switch later in the boot deliberately un-blanks over stale VRAM, so the banded display a cold boot shows for a few seconds is the old mode's bytes reinterpreted — real-hardware behaviour, not an error path (*observed*, [3]).
- **Pixel clocks.** The dot-clock synthesizer is programmed through the Cuda's I²C path (device address `$50`, registers 1–3, one Cuda transaction per parameter) rather than through any Control register — a Control model with no Cuda I²C path cannot change video mode ([tnt.md](tnt.md) §5.4 gives the 3.9064 MHz × 2^P × N/M law; [4] `drivers/video/fbdev/controlfb.c`).

### 3.5 Video input and the A/V panel

The video-input chain — the 8758 ADC, the 7196 decoder/scaler (DESC), and Plan B's two DBDMA channels (a write channel moving pixels out of the DESC's FIFO, a read channel fetching the 1-bit-per-pixel clip mask for play-through clipping) — is documented at family level ([tnt.md](tnt.md) §2.4, §4.5; [dbdma.md](dbdma.md) §1.2). This machine's facts:

- **Capability.** "The computer accepts video input for display (up to 24 bpp and up to 640 by 480 pixels at 30 frames per second), frame capture, or QuickTime movie capture" [1] p. 8. Input standards NTSC, PAL and SECAM on composite and S-video connectors [1] Table 1-2 p. 4.
- **The A/V panel, this machine's version.** The audio and video connectors are grouped on a back-panel A/V panel; "the A/V panel on the Power Macintosh 7500 is similar, but it does not have the video output ports" of the 8500 [1] §"Audio and Video Ports" p. 33. Fitted: S-video input, composite video input, stereo sound input and output; absent: S-video and composite video *output* [1] p. 33.
- **The S-video input connector is 7-pin, not 4-pin** — pins 5 and 7 carry an I²C clock and data line and pin 6 supplies +12 V at up to 250 mA [1] Table 3-9 p. 33. What the I²C pair addresses on this machine is not documented (§6.8).
- **No output encoder.** The Sixty6 RGB-to-YUV convolver and the 7187 DENC are "on the Power Macintosh 8500 computer only" [1] §"Video Subsystem ICs" p. 20; there is no television output stream, no genlock, and the family's second-stream VRAM accounting never applies.
- **DAV as an input source.** "The 7196 DESC IC can also accept video input data from the DAV connector" [1] §"Video Input" p. 21 — a PCI card can inject a stream into the same path (§4.2).

### 3.6 Storage, communications and audio

The device cells themselves — MESH, Curio (MACE/53C94/SCC), Cuda, AWACS, SWIM III — and their register files are [grand-central.md](grand-central.md) §2.5's; the DBDMA channel assignment behind them is [dbdma.md](dbdma.md) §1.4's. This machine's wiring:

- **Two SCSI buses, devices split by speed.** "The internal SCSI bus supports transfer rates up to 10 MB/second. (The external SCSI bus supports transfer rates up to 5 MB/second.)" [1] p. 8. The internal hard disk sits on the internal (MESH) bus [1] §"Internal Hard Disk Drive" p. 31; the Curio-served bus is "a SCSI bus for external SCSI devices and for the internal CD-ROM drive" [1] §"SCSI Port" p. 27, brought out on a 25-pin D-type connector while the internal CD-ROM uses a 50-pin one [1] p. 27.
- **Termination.** The external port has automatic termination — active with no external devices, removed when one or more are connected [1] p. 27. "The internal end of the SCSI bus is terminated by a 110 Ω passive terminator... located on the main logic board near the portion of the internal chassis connector that contains the signals for the internal CD-ROM drive. The internal CD-ROM drive does not include a terminator" [1] p. 28.
- **Ethernet: one port, two connectors.** "The Ethernet port accepts either a 10baseT cable or the Apple Ethernet adapter for thicknet or thinnet cables... The Ethernet port has two connectors but operates only one of them at a time. If devices are plugged into both connectors, the system defaults to the 10baseT connection" [1] §"Ethernet Port" p. 26.
- **Serial: two GeoPort-capable ports.** Both are 9-pin mini-DIN sockets accepting 8- or 9-pin plugs; "either port can be independently programmed for asynchronous or synchronous communication formats including AppleTalk and the full range of Apple GeoPort protocols" [1] §"Serial Ports" p. 24. Pin 7's GPi line connects to the SCC's data-carrier-detect input; pin 2's HSKi accepts an external clock at up to 920 Kbit/s; pin 9 supplies +5 V, with 500 mA total shared across the ADB and serial ports and no more than 100 mA per external device [1] p. 24. The ports support DMA transfers to and from main memory [1] p. 24.
- **ADB: one port, on the Cuda.** A single 4-pin mini-DIN port, pin 2 carrying the power-on (`PSW`) signal; the Cuda microcontroller drives the bus [1] §"Apple Desktop Bus (ADB) Port" p. 25.
- **Audio.** AWACS provides 16-bit stereo input and output at sample rates up to 44.1 kHz [1] §"AWAC Sound IC" p. 19. The sound input jack is a 1/8-inch stereo jack with a powered contact for Apple PlainTalk microphones (which draw power "by way of an extra-long, 4-conductor plug" [1] p. 29 note); input impedance 8000 Ω, maximum level 2 V rms, maximum gain 22.5 dB, signal-to-noise 82 dB [1] §"Sound Input Jack" p. 28. The sound output jack disconnects the internal speaker when a plug is inserted; output impedance 37 Ω, maximum level 0.9 V rms, maximum attenuation 22.5 dB, frequency response 20 Hz to 20 kHz ±2 dB, harmonic distortion plus noise under 0.05 percent, channel separation 80 dB (32 dB into 32 Ω headphones) [1] §"Sound Output Jack" p. 29. A PCI card can inject digital audio into AWACS through the DAV connector [1] p. 19.
- **Floppy.** One internal high-density Apple SuperDrive on a 20-pin connector, driven by the SWIM III cell in Grand Central, whose DMA design "does not require disabling of interrupts during floppy disk accesses" [1] pp. 18, 32.

### 3.7 The single Bandit and its one PCI bus

The bridge's register file, configuration mechanics, byte order and coherency handshake are [bandit.md](bandit.md)'s; PCI arbitration and the 33 MHz asynchronous relationship to the processor bus are [tnt.md](tnt.md) §2.1, §5.3's. This machine's bus, device by device:

| Occupant of the one PCI bus | PCI device number | Evidence |
|---|---|---|
| Bandit itself | 11 | [bandit.md](bandit.md) §3.2 |
| PCI socket 1 | 13 | *inferred — unverified* (§6.5) |
| PCI socket 2 | 14 | *inferred — unverified* (§6.5) |
| PCI socket 3 | 15 | *inferred — unverified* (§6.5) |
| Grand Central | 16 — "on Bandit 1's bus only" | [bandit.md](bandit.md) §3.2 |

The socket numbering is inferred from two agreeing facts: the firmware image's literal pool carries the `slot-names` mask `$E000` — bits 13, 14, 15 — in the bandit node construction [3], and the published device tree of the family's other one-bridge-per-three-slots machine shows that mask populated by exactly three sockets, labelled A1, B1, C1 ([bandit.md](bandit.md) §3.2.1). The 7500's own label strings were never published (§6.5).

The bus's electrical and mechanical contract, as the developer note states it for this machine:

- **Standard and signaling.** "The Power Macintosh 7500 and 8500 computers accept standard PCI cards as defined by the *PCI Local Bus Specification*, Revision 2.0. The cards are required to use the 5 V signaling standard and to use the standard ISA fence described in the specification" [1] §"PCI Expansion Slots" p. 49. The bus is "a nonsplit bus with 32-bit multiplexed address and data" at 33 MHz [1] p. 49.
- **Slot power.** "Each computer provides a total of 50 W of power for its three expansion slots. Both 5 V and 3.3 V are supplied; the total power at both voltages must not exceed the 50 W maximum" [1] p. 49.
- **Signals.** The sockets support all required PCI signals plus `/LOCK`-less optionals — specifically, they do **not** support the 64-bit bus extension, the cache support signals, JTAG boundary scan, `/LOCK`, or the error reporting lines `/PERR` and `/SERR` [1] Table 4-8 p. 50.
- **Arbitration.** A separate gate array fixes the priorities: Grand Central highest, then "PCI slots and Bandit master, in round-robin sequence: that is, each in turn, with equal priority" [1] §"Bandit PCI Bridge IC" p. 18 ([tnt.md](tnt.md) §5.3).
- **Where the DAV connector sits.** "Audio and video signals on the main circuit board are accessible through the DAV connector, which is located near one of the PCI expansion card connectors" [1] §"DAV Connector" p. 51 — its signals are board wiring adjacent to a socket, not a PCI device (§4.2).

The bandwidth consequence is the family's statement of this machine's structural limit ([tnt.md](tnt.md) §6.1): one bridge, one bus, three sockets, the DAV card and every I/O device sharing it. The onboard video is the one heavy traffic stream that does not contend — Chaos gives it its own bus ([tnt.md](tnt.md) §2.1).

## 4. Expansion

### 4.1 The three PCI sockets

Three sockets, PCI rev 2.0, 5 V signaling, ISA fence, 50 W shared power at 5 V and 3.3 V, no 64-bit extension, no cache-support signals, no JTAG, no `/LOCK`, no `/PERR`//`SERR` [1] pp. 49–50 (§3.7 above for the full statement). A card's interrupt is delivered through Grand Central's external lines, each socket's `/INTA`–`/INTD` pins OR-combined per slot ([bandit.md](bandit.md) §3.9); which external source each socket's line lands on for this board is not attested (§6.4).

The software contract for card writers has two machine-era quirks worth recording. Slot Manager calls "ordinarily... return an error result; the error code depends on the specific Slot Manager routine being called", unless a NuBus expansion chassis is present [1] §"Slot Manager Compatibility" p. 11. And the Vertical Retrace Manager still accepts `SlotVInstall()`/`SlotVRemove()`, but "in a PCI-based machine, the `dCtlSlot` field contains a pseudo-slot number that is assigned by the Display Manager during system startup... the number does not correspond to the physical location of the slot" [1] §"Setting Up a VBL Task" p. 70.

For users who must run NuBus cards, Apple's answer is external: "an external NuBus expansion chassis with two or three NuBus slots is available. The expansion chassis has a cable that connects it to one of the computer's PCI slots" [1] §"NuBus Expansion Cards" p. 11.

### 4.2 The DAV connector

The DAV connector is a 60-pin dual-row connector with 0.100-inch pin spacing [1] §"Signals on the DAV Connector" p. 52. It is the machine's route around the PCI bus for real-time media: "The DAV connector taps into the computer's video and sound data streams, providing access to the 4:2:2 unscaled digital video input signal and the digital audio input signal for the system's sound encoder/decoder (codec). By using the DAV interface, a PCI expansion card can capture or generate these signals without passing them through the PCI bus" [1] §"The DAV Interface" p. 51.

The pin set (Table 4-9 [1] pp. 52–53) makes the shape concrete: Y and UV component pairs (pins 11–26), a line-locked clock (28) with a clock reference qualifier (30), vertical sync (32) and HRef (36), a direction line (38), an I²C pair (39–40), analog audio left/common/right (42–44), digital audio input/output/clock/sync (46, 48, 50, 52), and the S-video Y and C components of the input stream (54, 56). A card can therefore take raw 4:2:2 video and digital audio in real time and move its compressed output over PCI — the two interfaces deliberately independent [1] p. 51. The 7196 DESC accepts this stream as a video input source alongside its own connectors [1] §"Video Input" p. 21, and AWACS accepts its digital audio [1] p. 19.

The authoritative specification is Apple's *Power Macintosh DAV Interface for PCI Expansion Cards* [5], which the developer note names twice for this purpose [1] pp. 19, 51. Note that this DAV interface is *not* the earlier generation's: "The DAV interface in the earlier Power Macintosh computers is not the same as the one in the computers that use the PCI bus" [1] p. 51 note.

### 4.3 The memory, VRAM and cache expansion paths

Three owner-installable expansion paths exist beyond the PCI sockets, all summarized in §3 and cross-referenced here: main memory to 1 GB across the eight paired DIMM slots (§3.2), VRAM from 2 MB to 4 MB across the four VRAM slots (§3.4), and the optional L2 cache SIMM from 256 KB to 4 MB (§3.3). The enclosure's hinged top chassis exists to make exactly these installations accessible [1] p. 7.

### 4.4 Internal drive bays

"The computer has space for two additional internal drives: one 5.25-inch drive (optional CD-ROM occupies this space) and one 3.5-inch drive" [1] p. 8 — one bay fewer in the 3.5-inch class than the 8500's two [1] p. 10. The internal hard disk options are 500 MB or 1 GB [1] p. 8. The optional CD-ROM is the AppleCD 600i: quadruple-speed, 600 KB/s sustained transfer, average access under 200 ms, SCSI burst rate above 3 MB/s, reading CD-ROM, CD-ROM XA, CD-I and PhotoCD discs plus audio [1] §"CD-ROM Drive" p. 31, Table 3-7. Which of the two SCSI buses the spare 3.5-inch bay's connector serves is not stated (§6.9).

### 4.5 What this machine does not expand by

- **No NuBus.** The machine "use[s] PCI cards for expansion and do[es] not have any NuBus expansion slots" [1] §"NuBus Expansion Cards" p. 11 — the external chassis of §4.1 is the only route.
- **No video output path.** The 8500's television encoder chain is not fitted and there is no connector for it; composite/S-video output can only come from a PCI card.
- **No second PCI bus.** The `$F4000000` slice of the family map ([tnt.md](tnt.md) §3.1) is unpopulated; a bridge cannot be added by the owner.
- **No multiprocessor path.** The MP surface is a property of dual-processor *cards* on the 9500-class boards ([hammerhead.md](hammerhead.md) §2.5–§2.7); the 7500's card slot carries one processor, and no dual-601 card exists in any evidence.

## 5. Boot sequence summary

The platform's boot contract — Open Firmware performs the hardware bring-up; `HWInit` is POST, not initialization; the five-step sequence from reset vector to `boot /AAPL,ROM` — is [tnt.md](tnt.md) §2.7's. This section walks those five steps with the 7500's branch points, each observed on the shipping ROM [3].

1. **Reset.** The 601 fetches its hardware-reset vector at `$FFF00100`, inside the ROM decode ([tnt.md](tnt.md) §3.4), and enters the NanoKernel.
2. **NanoKernel.** The configuration record's TNT constants apply: the interrupt controller at `$F3000000`, `InterruptHandlerKind = 2`, the kernel/emulator/dispatch data pages ([tnt.md](tnt.md) §3.5).
3. **Open Firmware.** The identity decodes of §1.2 run here, and their outcome is this machine's first branch point: `compatible = "AAPL,7500"`, and — decisively for everything downstream — the recognized identity makes the firmware instantiate the `chaos` and `control` display nodes, probe the display bus, and assign Control's BARs (`$18`, the 64 MB VRAM aperture, to `$90000000`; `$14`, the 4 KB register block, to `$94000000`) ([bandit.md](bandit.md) §3.10; [3] *observed*). The tree carries one `bandit` node, Grand Central with all cells including `mesh`, and no second bridge. On a blank or corrupted nonvolatile store the firmware reformats it and clears the Mac OS PRAM partition before the OS reads it ([tnt.md](tnt.md) §2.7).
4. **POST.** The diagnostics object reads the Hammerhead identifier (TNT arm), runs the BoxID bit-8 factory-test check, and logs into NVRAM through Grand Central's apertures ([tnt.md](tnt.md) §2.7; [grand-central.md](grand-central.md) §2.6). The L2 test is skipped entirely on a factory machine — no SIMM, so `+$E0`'s presence bit reads clear ([hammerhead.md](hammerhead.md) §4.4).
5. **`boot /AAPL,ROM` and the classic start-up.** The 68k emulator takes over; the 68k identification routine synthesizes `$3021` and selects the 7500 product record (kind byte `$3E`), which installs the TNT decoder record ([hammerhead.md](hammerhead.md) §4.3; [tnt.md](tnt.md) §3.6) — `BoxFlag` reads `$3E` and gestalt reports machine type 68 (*observed*, [3]). The ROM's native Control driver then mode-sets the built-in display (the 640×480, 32 bpp boot mode of §3.4; *observed*, [3]) — the step the video-less 9500 skips ([tnt.md](tnt.md) §2.7). The Start Manager honours the PRAM default boot device first, so a cold boot from zeroed PRAM with no disk at the recorded ID looks stalled for roughly thirty guest-seconds before the drive-queue walk proceeds ([tnt.md](tnt.md) §2.7, *observed*).

The interrupt plumbing this start-up depends on — the Grand Central classification into 68k levels, the VIA1/Cuda cascade, the 60.15 Hz tick — is [tnt.md](tnt.md) §5.1's and [grand-central.md](grand-central.md) §3.2–§3.5's; nothing in it is unique to this machine.

## 6. Open questions

1. **Which ROM release this machine shipped with.** Both August 1995 releases serve the 7500 identically in every component the identity decodes touch ([tnt.md](tnt.md) §1.3); no Apple document pins a model to a release.
2. **The complete `AAPL,cpu-id` value on a real 7500.** The construction is decoded ([hammerhead.md](hammerhead.md) §4.3), but the value folds in Hammerhead `+$30`'s nibble and BoxID bits 11–15, whose live values on a real board are unattested ([tnt.md](tnt.md) §7 item 3).
3. **Whether this machine's firmware emits a `planb` node.** The video-input hardware is fitted (§3.5) and the firmware image carries `planb` and `sixty6` literals, but the per-model emission of the AV nodes was never established — the tree observations pin `chaos`/`control` only ([tnt.md](tnt.md) §4.5, §7 item 9).
4. **The per-socket PCI interrupt assignment.** Which Grand Central external source each socket's combined `/INTA` line lands on for this board is not attested in any Apple document; only the 9500's table is published ([grand-central.md](grand-central.md) §3.2; [bandit.md](bandit.md) §3.9).
5. **The socket IDSELs and label strings.** The `$E000` slot mask in the firmware's bandit-node construction and the 9500's published Bandit-1 labels (A1/B1/C1) together imply IDSEL 13–15 with those labels on this machine [3]; [bandit.md](bandit.md) §3.2.1 — but no published source shows this machine's own `slot-names` property, so the inference is unverified.
6. **BoxID's remaining bits on this board.** Only bits 11 and 13 are consumed by the decodes; the strap field, the MESH-present and pull-up bits circulate from community teardowns only ([tnt.md](tnt.md) §7 item 4). The active polarity of the bit-8 factory-test strap in particular differs between the recorded observation campaigns, and no Apple document states it.
7. **The VRAM SIMM's connector and module specification.** The developer note gives full pin tables for the RAM DIMM and the L2 cache SIMM but none for the VRAM SIMM — its pinout, speed grade and the two-bank aperture geometry a sizer must model are established only from driver behaviour ([3]; [4] `controlfb.c`).
8. **What the S-video input connector's I²C pair addresses.** Pins 5 and 7 of the 7-pin input connector carry an I²C clock and data line [1] Table 3-9 p. 33; the device they serve (presumably the input decoder chain) is not documented.
9. **Which SCSI bus serves the spare 3.5-inch bay.** The hard disk uses the internal (MESH) bus and the CD-ROM the external-bus (53C94) side [1] pp. 27, 31, but the note never says which connector the expansion bay attaches to.
10. **The 601 timebase as the firmware publishes it.** The `timebase-frequency` literal was never isolated in the firmware's CPU node ([tnt.md](tnt.md) §7 item 5); the 0.27 percent RTC discrepancy of §2.2 is documented [1] p. 72, but the published rate is not.
11. **What the firmware reads to derive `bus-frequency` on a card swap.** The bus clock is the card's property ([tnt.md](tnt.md) §2.2); whether a 604-class card in this socket changes the published value, and from which source the firmware takes it, is unattested ([tnt.md](tnt.md) §7 item 12).
12. **The `mesh` node's `clock-frequency` as this ROM publishes it.** The 53C94's 25 MHz literal is decoded; the mesh node's own clock literal was not, and shipping drivers simply assume 50 MHz ([tnt.md](tnt.md) §5.4).
