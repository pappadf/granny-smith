## 1. Overview

### 1.1 What the part is

**Egret** is a single-chip system-management microcontroller: "a custom version of the Motorola 68HC05
microcontroller" [1] ch. 1 that concentrates, in one part, the functions earlier Macintosh main logic boards
spread across a custom ADB transceiver chip, a discrete real-time-clock chip and power-control circuitry.
On the Macintosh IIsi it "integrates the functions of the ADB controller, RTC (real-time clock), PRAM
(parameter RAM), soft power control, power-on reset, keyboard reset, and NMI (nonmaskable interrupt). In
previous Macintosh models, these functions were provided by separate devices on the main logic board" [1]
ch. 5. Apple's internal hardware survey of February 1991 names the part and its design twice: "The Egret
(also known as the ADBμ) is an 68HC05 8-bit single-chip microprocessor" [2] p. 55, and — in the same
document's system-support chapter — the design "is based on the Motorola 68HC05EG 8-bit microprocessor,
and currently exists in two implementations: Egret and Cuda. The Egret is also known as the µADB" [2] p. 58.

The two new functions the IIsi note calls out are **programmable wakeup** and **file server mode** [1]
ch. 5 (§3.8); the power-off control bit that older machines kept in their custom logic (on the IIci, the RBV's
— [rbv.md](rbv.md) §3.9) is Egret's on the IIsi ([mdu.md](mdu.md) §2.5).

Egret's documented successor is **Cuda**, which "is an improved version of Egret with higher ADB
performance" [2] p. 55 — the improvement being a change "in the 68HC05 code which improves the ADB transfer
performance by more efficiently handshaking the ADB transfers" [2] p. 59. The successor's transport,
packet protocol and command set are fully documented on its own page ([cuda.md](../av/cuda.md) §2–§4);
this page cites them as contrast and flags every point where Egret's own assignments are *not* in the
evidence (§6). The Egret page is the honest thin one of the pair: the IIsi Developer Note describes the
part functionally, the Hardware Overview adds the transport's shape and the function list, and the
specification Apple names for the full detail — the *Elsie/Catalina ADBu ERS* [2] p. 59 — is not in this
evidence set, nor is any Egret firmware image or IIsi ROM disassembly ([mdu.md](mdu.md) §7, item 15).

The host never addresses a register of Egret's. The microcontroller sits on the far side of a bit-serial
link whose host end is VIA1 — "a clock (generated by the ADB controller), bidirectional data, and two mode
lines" [2] p. 55 — and every transaction, in both directions, is a packet on that link (§2, §3.2).

### 1.2 Which machines carry it

| Buccaneer (unreleased 40 MHz 68030 design) | the same MDU/RBV/NuChip30/Egret chip set as the IIsi, per the then-current comparison table | [2] Table 1.5, [mdu.md](mdu.md) §6.3 |
| Eclipse, Spike (then-unreleased designs) | RTC/PRAM only on Eclipse — its ADB runs through the IIfx-style PICs; RTC/PRAM on Spike, whose ADB row is the classic chip-and-VIA | [2] Table 1.5 |

Cuda replaces Egret on the machines that follow ([cuda.md](../av/cuda.md) §1.2). The scheme itself — a
battery- or trickle-backed microcontroller owning clock, PRAM, ADB and power — had a precedent in the
Macintosh Portable's Power Manager IC, "a Mitsubishi M50753 microprocessor, which contains its own RAM and
ROM… and [acts] as the real-time clock and as the ADB transceiver" [3] ch. 2 p. 75 note; Egret brings that
organization to the desktop mainstream.

### 1.3 Division of labor

Egret owns functions, not buses. The split that keeps this page honest:

| Function | Owner | Where documented |
|---|---|---|
| ADB device protocol — command byte, Talk/Listen/Flush, service request | Egret executes it; the protocol itself is specified once at [ADB](../../hardware/adb.md) | [1] ch. 5, [5] |
| ADB *content* — key codes, mouse deltas, device handler IDs | the devices | [keyboard.md](../../hardware/keyboard.md) §6, [ADB](../../hardware/adb.md) §"Mouse" |
| PRAM *medium* — the 256 battery-backed bytes and the read/write path | Egret (§2.5, §3.5) | [2] p. 58 |
| PRAM *layout* — which offset holds the startup device, the alarm, the volume | the ROM/OS convention | [PRAM format](../../formats/mac-pram.md) |
| Real-time clock — the 32-bit seconds counter | Egret (§3.5) | [1] ch. 5 |
| Soft power on/off, wake, reset pulse, PFW | Egret, plus the PSU's trickle rail (§3.6) | [1] ch. 5 |
| The transport's host end — the VIA1 register bank, timers, port bits | VIA1, a real 6523-class part on the IIsi board | [via.md](../../hardware/via.md), [mdu.md](mdu.md) §3.3 |
| Interrupt levels and concentration (everything except Egret's own lines) | the RBV, VIA2's replacement | [rbv.md](rbv.md) §3.1, [mdu.md](mdu.md) §5.1 |
| Reset and NMI switches | none exist — the keyboard, through Egret, replaces them (§3.7) | [1] ch. 5 |

The load-bearing negative facts: VIA1 port B carries **no real-time-clock lines** on the IIsi (§2.2), the
RBV concentrates every other interrupt ([rbv.md](rbv.md) §3.1), and the MDU comes out of reset first because
Egret's Test signal reaches it before the processor's Reset does ([mdu.md](mdu.md) §2.5).

### 1.4 The documented function list

The Hardware Overview enumerates what the Egret/Cuda scheme adds to the ADB functions it "emulate[s] …
handled by the earlier ADB chip" [2] p. 58 (that earlier chip being the customized 4-bit microprocessor,
Apple part 342S0440 [2] p. 55):

- soft power-on control and power-on **RESET** [2] p. 58
- **256-byte parameter RAM** [2] p. 58
- **flash-ROM write enable** (if used) [2] p. 58
- **keyboard-invoked and programmer's-switch NMI** [2] p. 58
- **keyboard-invoked and programmer's-switch RESET** [2] p. 58
- **file-server auto-power-up** [2] p. 59
- **monitor connected detection** (if used) [2] p. 59

The two "if used" entries are board wiring options, not IIsi commitments: no document assigns the IIsi's
video sense to anything but the RBV ([rbv.md](rbv.md) §3.5), and no document in this evidence set names a
flash-ROM part on any Egret machine (§6, item 9). The "programmer's switch" wording is generic to the
scheme; on the IIsi there is no switch at all (§3.7).

### 1.5 Standby power

Egret lives on the machine's battery- and trickle-backed power domain, not the main CPU rail. "Even when
power is off, the power supply maintains a +5-V trickle output that allows the microcontroller to poll the
keyboard and rear-panel power switches" [1] ch. 5; "a trickle power supply or battery allows the ADB
microcontroller to continue counting and preserves the PRAM data even when the Macintosh IIsi computer is
turned off or unplugged" [1] ch. 5. The keyboard power key arrives over the ADB connector's dedicated
power-on pin — pin 2, "momentarily grounded to pin 4 to turn on the power supply", held to the trickle
rail through 100 kΩ, with "Power … never … drawn through this pin" [1] Table 5-5 — the same path the II
family has used since the trickle-charged switching capacitor of the IIcx/IIci ([mdu.md](mdu.md) §2.5,
[3] ch. 6 pp. 244–245). The ADB connector's full pinout is [1] Table 5-5: pin 1 Data (bidirectional,
open-collector, pulled to +5 V through 470 Ω), pin 2 Power on, pin 3 Power (+5 V behind a 1-ampere fuse),
pin 4 Return (ground).

### 1.6 Clocking

No document in this evidence set states Egret's own clock or crystal. The function it implements requires
a timebase: the classic RTC chip it replaces "has its own 32.768KHz oscillator, and is powered by an
on-board alkaline or lithium battery" [2] p. 58, and the successor's only documented clock is a 32.768 kHz
crystal ([cuda.md](../av/cuda.md) §1.5). Whether Egret uses the same figure, and whether one timebase
serves both the 68HC05 core and the seconds counter, is open (§6, item 4).

## 2. Register file

### 2.1 What software can address

**Nothing of Egret's, directly.** Egret has no CPU-mapped register bank: it sits behind VIA1, and its
software surface is (a) the VIA1 registers of the host end and (b) the packet command surface the transport
carries (§2.4). The register file this section documents is therefore the host end's — the same 6522-class
bank every Macintosh since the original carries — plus what is known of the microcontroller's own map at
the far end.

The IIsi's VIA1 occupies the family's I/O island at **$5000 0000–$5000 1FFF**, address lines A9–A12 wired
as the register select ([mdu.md](mdu.md) §3.3), so internal register *n* sits at $5000 0000 + *n* × $200 on
the upper data byte — the layout tabulated at [via.md](../../hardware/via.md) §"Register Map". The
transport touches four of those registers, and the classic 6522 semantics of each are specified on the VIA
page and are not restated here:

| VIA1 register | Offset | Role in the Egret transport |
|---|---|---|
| vSR — shift register | +$1400 | the byte pipe: written by the host, filled by Egret's clock (§2.3) |
| vACR — auxiliary control | +$1600 | the SR mode/direction bits — the SR runs under an external clock, Egret's (§2.3) |
| vIFR — interrupt flags | +$1A00 | the SR-completed interrupt, once per byte |
| vIER — interrupt enables | +$1C00 | the SR interrupt's enable, classic set/clear top-bit semantics |
| vBufB / vDirB — port B | +$0000 / +$400 | the three handshake lines of §2.2 and their direction bits |

Which exact ACR mode value the IIsi ROM writes, and whether it flips the direction bit per transaction the
way the successor's ROM demonstrably does ([cuda.md](../av/cuda.md) §2.2), is not pinned by any citable
document (§6, item 2); the SR-under-external-clock family of modes is the only class consistent with "a
clock (generated by the ADB controller)" [2] p. 55.

### 2.2 Port B bit map (host view)

VIA1 port B is the transport's handshake surface. On the IIsi the II-family's RTC bits are gone — the
Overview's VIA appendix lists no clock lines on the IIsi's port B, where the IIci column carries
RTC.DATA/RTC.CLK/RTC~ on PB0–PB2 [2] Appendix 1 pp. 63–64 — and the three lines that replace them are the
ones the appendix names for the IIsi:

| Port B bit | Line (appendix name) | Direction | Meaning |
|---|---|---|---|
| 0–2 | n.c. on the IIsi (RTC lines on the IIci) | — | no discrete RTC exists behind VIA1; the clock lives inside Egret |
| 3 | session ("CVR session") | host input | Egret's session line: asserted while Egret has traffic for the host (*inferred* — active-low by the convention of the classic ADB.INT~ line this bit replaces [2] Appendix 1, and of the successor's TREQ [cuda.md](../av/cuda.md) §2.3) |
| 4 | "VIA full" | host output | a host-to-Egret handshake line (*inferred* direction, as one of the "two mode lines" of the interface [2] p. 55) |
| 5 | "system session" | host output | the host's transaction-in-progress line (*inferred* direction, same basis) |
| 6–7 | n.c. on the IIsi (parity lines on the IIci) | — | — |

Two provenance caveats. First, the appendix's OCR in this evidence set is partially damaged: the IIsi
column's PB0/PB1/PB6/PB7 read as no-connects and the three session/full labels survive as a group whose
bit-for-bit alignment with PB3–PB5 is reconstructed from the neighbouring columns (*observed* in the
printed appendix, pp. 63–64, with damaged text). Second, the *directions* are not printed anywhere: the
inference rests on the classic ADB chip's use of the same three bits (ADB.INT~ an input on PB3, ADB.ST0
and ADB.ST1 outputs on PB4/PB5 — the IIci's own column [2] Appendix 1 pp. 63–64) and on the successor's
identical assignment ([cuda.md](../av/cuda.md) §2.3). The per-byte edge semantics — which line the host
toggles per byte, and how the last byte of a packet is signalled — are not documented for Egret (§6,
item 2).

### 2.3 The shift-register path: CB1 and CB2

The remaining two wires of the five-wire transport are the VIA's CB1 and CB2, which the appendix still
labels **ADB.CLK** and **ADB.DATA** [2] Appendix 1 pp. 63–64. The clock is generated by the microcontroller
— "a clock (generated by the ADB controller), bidirectional data" [2] p. 55 — so **Egret is the shift-clock
master in both directions**, exactly as the successor's firmware is ([cuda.md](../av/cuda.md) §3.1): the
host never paces a transfer by clocking bits itself; it hands whole bytes to the SR and takes whole bytes
back. "The ADB unit can generate an interrupt, which is processed by VIA1" [2] p. 55 — the per-byte SR
interrupt of the table in §2.1 is that interrupt.

### 2.4 The command surface

"Commands use a packet structure protocol with extended pseudo-device commands" [2] p. 59. That single
sentence is the extent of what the citable evidence prints about Egret's command set: a framed packet
protocol, with management commands carried as an extension of the ADB device-command structure rather
than as a second bus. The successor's command surface — packet type bytes, a response header of
[type][flags][command], twenty-five management opcodes, error packets — is documented end-to-end
([cuda.md](../av/cuda.md) §3.6–§3.7) because the successor's firmware image and two generations of ROM
disassembly exist; **for Egret, none of the specific assignments are printed in any document of this
evidence set** (§6, item 1). The page deliberately does not restate the successor's tables as if they were
Egret's.

### 2.5 The Egret side: the 68HC05's own map

The microcontroller's internal memory map is not documented in this evidence set. What is pinned is its
*contents*, by function: the **256-byte parameter RAM** [2] p. 58 lives inside the part (there is no
separate RTC/PRAM chip on the IIsi board — [mdu.md](mdu.md) §4.2), the **32-bit seconds counter** [1]
ch. 5 lives inside it, and the **wakeup flags are "contained in the code of the ADB microcontroller"**
[1] ch. 5 — held in the microcontroller's own store, not in a host-visible location. Whether the PRAM
occupies a single 256-byte page of the 68HC05 address space the way the successor's does — and whether a
management command reaches beyond it into the microcontroller's RAM and registers at all ([cuda.md](../av/cuda.md)
§3.7, the read/write-MCU-address pair) — is open (§6, item 7).

### 2.6 Reset state

No document states Egret's power-on state — the port latches, the enabled interrupts, the autopoll and
tick defaults — and the VIA1 side is governed by the standard 6522 reset behaviour (all peripheral lines to
input, timers/shift register/interrupt logic disabled; [via.md](../../hardware/via.md) §"Reset
Behavior"). The host's boot code writes the VIA registers it needs before relying on them ([iisi.md](iisi.md)
§9); nothing in the evidence set shows Egret's own reset values (§6, item 8).

## 3. Behaviour

### 3.1 The transport in one paragraph

The link is five wires: the three port-B lines of §2.2 plus CB1 (Egret's shift clock) and CB2 (the
bidirectional data path through the VIA's shift register) [2] p. 55, Appendix 1 pp. 63–64. The host side of
the mechanism is the one the Guide describes for the classic ADB transceiver and Egret inherits: "The ADB
Manager or device driver sends commands for an ADB device to the VIA 1 byte at a time. The VIA holds the
byte in an internal register and shifts it out 1 bit at a time to the ADB transceiver" [3] ch. 2 p. 75 — and
in the other direction a device's service request makes the transceiver "send[] an interrupt request to the
VIA, which interrupts the CPU" [3] ch. 2 p. 75. "These designs emulate the ADB functions handled by the
earlier ADB chip" [2] p. 58, so the byte-at-a-time, interrupt-per-event shape carries across; what changes
is that the controller on the far end is a system manager with a packet protocol instead of a bare ADB
transceiver, and that the management traffic rides the same wires (§3.2).

### 3.2 The packet protocol

Every transaction, in both directions, is a packet with "extended pseudo-device commands" [2] p. 59.
Documented shape: commands are framed packets; management (pseudo-device) commands extend the ADB device
command structure; ADB interrupts are "passed to the VIA1 (or equivalent)" and interrupts from the pseudo
functions reach the processor separately (§3.3) [2] p. 59. Not documented: the packet type byte values, the
response header layout, the opcode assignments, the error reporting, the data-length convention — nothing
of the byte-level protocol is printed for Egret (§6, item 1). The *Elsie/Catalina ADBu ERS*, which the
Overview names as holding "a full description of the Egret interactions with the 680XX, ADB state diagrams,
and signal timings" [2] p. 59, is the document that would close the gap; it is not in this evidence set.

### 3.3 Interrupts

Egret's traffic reaches the processor on two documented paths:

1. **ADB interrupts → VIA1.** "The ADB unit can generate an interrupt, which is processed by VIA1" [2] p. 55;
   "ADB interrupts are passed to the VIA1 (or equivalent)" [2] p. 59. On the IIsi the "or equivalent" is
   the real VIA1; VIA1's interrupt sits at level 1 of the family's RBV-concentrated interrupt architecture
   ([rbv.md](rbv.md) §3.1, [mdu.md](mdu.md) §5.1).
2. **Pseudo-function interrupts → the processor's interrupt pins.** "Interrupts from the pseudo functions
   are passed to the 680XX processor by three tri-state lines that connect to the processors interrupt
   vector pins, IPL0..2 (Mac LC)" [2] p. 59 — the documented wiring for the Mac LC, where the
   one-second tick and the management events enter the machine as priority-level drives rather than as VIA
   interrupts. The IIsi's arrangement is pinned only at one end: the Overview's RBV input list for the IIsi
   shows **NMI at level 7** [2] Appendix 1 pp. 63–64, and the family's interrupt architecture routes level 7
   to the NMI ([rbv.md](rbv.md) §3.1). Whether the IIsi's Egret drives the IPL pins directly (LC style) or
   feeds the RBV, and how the one-second tick is delivered on the IIsi at all, is open (§6, item 5).

### 3.4 ADB

The ADB is "a single-master, multiple-slave serial communication bus, with asynchronous protocol"
connecting keyboards, mice and tablets to the machine; "the custom ADB microcontroller drives the bus and
reads status from the selected external device" [1] ch. 5. The IIsi supports "a maximum of three chained
devices" [1] ch. 1. The device protocol — command byte, register model, Talk/Listen/Flush, service
requests, addresses, the keyboard and mouse register formats — is specified once at [ADB](../../hardware/adb.md)
and is not restated here; the devices' content is [keyboard.md](../../hardware/keyboard.md) §6 (key codes)
and [ADB](../../hardware/adb.md) §"Mouse" (delta packets).

Egret's own documented performance signature is a *deliberate slowness*: "Egret waits the worst-case time
before completing an ADB transfer" [2] p. 59 — the property Cuda's recoded handshake was written to remove
([cuda.md](../av/cuda.md) §1.1). A host-side consequence, drawn from the same sentence: ADB turnaround on
an Egret machine is bounded by that worst case, not by the devices.

Whether Egret's firmware carries **in-controller auto-polling** — the successor's autonomous
Talk-register-0 sweep with a host-installed device bitmap ([cuda.md](../av/cuda.md) §3.8) — is not printed.
The classic machines' ROM drives polling itself over the transceiver ([ADB](../../hardware/adb.md)
§"Auto-Polling (ROM-Driven)"); which model Egret firmware implements is open (§6, item 6).

### 3.5 The real-time clock and parameter RAM

The microcontroller "includes a 32-bit counter that operates similarly to the RTC chip used in other
members of the Macintosh II family" [1] ch. 5 — the classic chip's seconds register and its use are
specified at [RTC](../../hardware/rtc.md), including the 1904-epoch seconds convention and the one-second
interrupt that chip generates through VIA1. Battery or trickle power keeps Egret's counter running "and
preserves the PRAM data even when the Macintosh IIsi computer is turned off or unplugged" [1] ch. 5. The
PRAM is **256 bytes** [2] p. 58 — the size the classic chip reached through its extended 8-sector-of-32
addressing with a 20-byte direct window for the oldest part's compatibility [2] p. 58; the byte *layout*
is the ROM/OS convention at [PRAM format](../../formats/mac-pram.md) and lives outside this page.

"Access to the RTC or PRAM is different from previous Macintosh computers. It is accomplished through
modified ADB style commands. Software that uses the existing driver routines … will continue to work …
without any problems. However, any software that attempted to address the hardware directly will not
work" [1] ch. 5. Whether Egret's PRAM sits behind any write-protect mechanism comparable to the classic
chip's ([RTC](../../hardware/rtc.md) §"Special Commands") is not documented (§6, item 7).

### 3.6 Soft power

The power-control design is the II-family's soft power ([mdu.md](mdu.md) §2.5) with Egret as the switching
agent: "I/O ports and software on the ADB microcontroller poll inputs from the keyboard power switch or
the rear-panel power switch and control the power supply through the power fail warning (PFW) signal to
the power supply and the expansion interface" [1] ch. 5 — note that PFW is exported to the expansion
connector as well as to the supply, so a PDS card sees the machine's power state. The documented sequence
rules [1] ch. 5:

| Event | Behaviour |
|---|---|
| Keyboard power key, or rear-panel switch, pressed while off | PFW goes high; the supply turns on **within 2 seconds** |
| Rear-panel switch pressed while on | a **hard off after 2 milliseconds**, "without notifying software" |
| Shutdown menu command | software sends "a special command that enables the ADB microcontroller to pull PFW low", letting pending activity finish before the supply drops |
| Rear-panel switch locked on | the machine re-powers itself after an AC outage — the file-server recovery feature |
| Programmed wakeup | software arms an automatic power-on at a set time (§3.8) |

### 3.7 Reset and NMI

**Power-on reset.** "When the ADB microcontroller turns the power supply on, it also asserts the Reset and
Test signals. The Test signal, which has a shorter time constant than Reset, is used to reset the MDU. It
allows the gate array to initialize the RAM controller and the I/O decode circuits before the processor
attempts to execute any cycles. The Reset signal, which goes to the 68030 and other I/O devices, has a
longer time constant than Test and allows the processor to stabilize before executing any cycles" [1]
ch. 5. The MDU is therefore the first device out of reset on the IIsi, by design — the family-level
consequence is drawn at [mdu.md](mdu.md) §2.5 and is not restated here.

**Keyboard reset and NMI.** "There are no external reset or NMI switches (commonly referred to as
programmers switches) on the Macintosh IIsi computer. These functions are now controlled from the keyboard
by the custom ADB microprocessor" [1] ch. 5:

| Sequence | Effect |
|---|---|
| Command key + power button | asserts **NMI** — "a diagnostic signal that enables the debugging software to halt execution of an application and change to a debugger" |
| Command key + Control key + power button | **hard reset**, "identical to a power-on reset" |

Both sequences must be held "for at least 1 second to allow the microcontroller enough time to respond to
the NMI or hard-reset signal" [1] ch. 5 — the microcontroller is polling, not latched. **NMI is off by
default**: "It must be turned on (using a new cdev) before it can be asserted. The assumption is that most
users are not programmers" [1] ch. 5. The key sequences "were chosen for compatibility with currently
existing Macintosh utility software" [1] ch. 5 — the same chords the programmer's-switch-aware utilities
already knew. The machine-page summary is [iisi.md](iisi.md) §13.5.

### 3.8 Wakeup, network boot and file-server mode

Three autonomous-boot functions live in the microcontroller [1] ch. 5: a **programmable wakeup time** —
"a function that allows setting of a wakeup time, causing the Macintosh IIsi computer to automatically
power up at a specified time and perform an operation", with the wakeup flags "contained in the code of
the ADB microcontroller" and controlled by software; a **network-boot flag** — set from the Control Panel,
it "causes the system to start up over a communications network such as Ethernet or LocalTalk", aimed at
classroom diskless operation; and **file-server auto-power-up** [2] p. 59 — the locked-switch recovery
behaviour of §3.6 plus the auto-restart expectations of a server machine. The wakeup time's representation
(seconds against the counter, as the successor's alarm comparator does — [cuda.md](../av/cuda.md) §3.9)
is not printed for Egret (§6, item 10).

### 3.9 Sound control: the LC's DFAC

One board documents a sound-system duty: "The ADB microcontroller also controls the DFAC (Digitally
Filtered Audio Chip), a custom IC that performs the analog processing functions of the sound system" [4]
ch. 12 p. 270 — a sentence printed in the Macintosh LC chapter of the card-design book, whose context is
the LC board ("This microcontroller is also used in the Macintosh IIsi" [4] ch. 12 p. 270). The IIsi's own
sound path is the ASC with two Sony filter/driver chips and contains no DFAC ([mdu.md](mdu.md) §4.2, [1]
ch. 5), so the DFAC control is LC wiring; whether the IIsi's Egret firmware retains the sound-control
command at all is not documented (§6, item 11). The successor's firmware keeps a DFAC command as a legacy
sound-control string ([cuda.md](../av/cuda.md) §3.7).

### 3.10 Monitor connected detection

"Monitor Connected Detection (if used)" [2] p. 59 is in the scheme's function list, but no document wires
it: on the IIsi the monitor sense lines belong to the RBV ([rbv.md](rbv.md) §3.5), and which board, if
any, routed a sense path through the microcontroller is not established (§6, item 12).

## 4. Programming model

### 4.1 What the host drives

The ROM and OS drive Egret through VIA1 and the packet protocol — never through a register of the
microcontroller's own (§2.1). The compatibility contract the IIsi note states three times:

- **High-level software is unaffected.** "Software that uses the existing driver routines to gain access
  to the RTC and the PRAM will continue to work on the Macintosh IIsi computer without any problems" [1]
  ch. 5, and the ADB Manager's interface carries across: applications that use it work [1] ch. 1,
  [iisi.md](iisi.md) §13.2.
- **Direct-hardware software breaks.** "If you have developed applications that address the ADB hardware
  directly, they will probably not function under this new scheme" [1] ch. 1; "any software that attempted
  to address the [RTC/PRAM] hardware directly will not work" [1] ch. 5.
- **Debuggers must change.** "You will have to revise debuggers to support the keyboard-based NMI" [1]
  ch. 1 — the debugger's programmer's-switch assumption dies with the switch.

### 4.2 Boot, and what is not pinned

The documented bring-up fact is the power-on reset sequence of §3.7: Egret asserts Test, then Reset, and
the MDU initializes before the 68030 runs its first cycle [1] ch. 5. Beyond that, **the IIsi ROM's own
Egret traffic is not pinned by this evidence set**: no annotated IIsi ROM disassembly exists
([mdu.md](mdu.md) §7, item 5), so the controller-initialization routine, the sync-or-equivalent first
transaction, the PRAM read path the start-up code actually issues, and the order in which the tick,
autopoll and power functions are enabled are all open (§6, items 1, 5, 6). The successor's boot flow —
sync cycle before RAM exists, early PRAM reads over a polled transport, manager installation, then
autopoll and tick enabled by command ([cuda.md](../av/cuda.md) §4) — is the documented shape of the same
host lineage one firmware generation later, and a reasonable target for what an IIsi bring-up must
accomplish; it is *inferred*, not evidence, that the IIsi ROM follows the same arc.

### 4.3 Observed host behaviour

Recorded guest sessions bound one timing property a re-implementation needs: the IIsi ROM and OS take up
Egret's unsolicited first byte promptly — in recorded IIsi boots under System 6.0.8 through System 7.5,
the host engages the controller's presented byte within roughly a millisecond of its presentation
(*observed* in recorded guest boots). The bound matters in one direction only: a controller model may
present a byte and expect service on this order, but nothing in the evidence bounds how long Egret waits
for a host that never comes — the successor's host-side budgets are documented ([cuda.md](../av/cuda.md)
§3.12); Egret's own watchdog, if any, is not (§6, item 13).

### 4.4 Shutdown and restart as the OS issues them

Shutdown is the documented flow of §3.6: the OS sends the command, Egret pulls PFW low, the machine dies
with its pending activity complete [1] ch. 5. Restart — a command-driven reset pulse without power removal —
is documented for the successor ([cuda.md](../av/cuda.md) §3.11) but not for Egret; whether the IIsi's
controller offers a restart command, or whether the IIsi OS restarts by re-running the power-on path, is
open (§6, item 14).

## 5. Quirks & errata

- **No programmer's switches exist.** NMI and hard reset are keyboard chords through the microcontroller,
  and NMI ships **disabled** until a cdev enables it [1] ch. 5 — a debugger that assumes a switch, or a
  user who assumes NMI works out of the box, is wrong on this machine.
- **The chords must be held a full second.** The microcontroller polls; a tap is not a command [1] ch. 5.
- **Direct ADB- and RTC-hardware software breaks, silently by design.** The note's compatibility
  statements are absolute: driver-level software works, register-poking software does not [1] ch. 1, ch. 5.
- **VIA1's II-family RTC bits are gone.** On the IIsi, port B bits 0–2 are no-connects — the clock and PRAM
  live inside the microcontroller — so any code that bit-bangs the classic RTC lines through VIA1 writes
  nothing [2] Appendix 1 pp. 63–64.
- **Egret completes every ADB transfer at the worst case.** The documented performance signature, and the
  stated reason the successor exists [2] p. 59.
- **PFW is exported to the expansion connector.** The power state is a PDS-visible signal, not just a
  supply-internal one [1] ch. 5.
- **The rear-panel switch is a hard off while running** — power drops 2 ms after the press, with no
  software notification [1] ch. 5. Only the locked-on position gives the file-server recovery behaviour.
- **The power-on pin is sense-only.** ADB connector pin 2 may be shorted to ground to request power, but
  "Power should never be drawn through this pin" [1] Table 5-5.
- **The clock and PRAM survive unplugging.** Trickle *or* battery keeps the counter running and the PRAM
  intact [1] ch. 5 — a machine left unplugged for a working battery comes back with the right time.
- **The NMI/reset chords were chosen for compatibility** with existing Macintosh utility software [1]
  ch. 5 — the utility chords transfer, the switch hardware does not.

## 6. Open questions

1. **The packet protocol's byte-level assignments.** Packet type values, response header layout, opcode
   assignments, error reporting and data-length convention are printed nowhere for Egret; only the
   existence of "a packet structure protocol with extended pseudo-device commands" is documented [2] p. 59.
   Whether Egret's values match the successor's documented set ([cuda.md](../av/cuda.md) §3.6–§3.7) is
   unestablished. The *Elsie/Catalina ADBu ERS* [2] p. 59 — or an Egret firmware dump — would close this
   and items 2, 7 and 8 at once.
2. **The per-byte handshake semantics.** Which of PB4/PB5 the host toggles per byte, what the session line
   means edge-by-edge, how the last byte is signalled, and which ACR mode value the IIsi ROM writes: the
   evidence prints "two mode lines" [2] p. 55 and the appendix's line names [2] pp. 63–64, and nothing
   more.
3. **The core beyond the family level.** The Overview says the design is "based on the Motorola 68HC05EG"
   [2] p. 58 and the IIsi note "a custom version of the Motorola 68HC05" [1] ch. 1; no Egret datasheet,
   Apple part number or firmware identity is in the evidence set, so the production die and its firmware
   revisions are unpinned (the successor's part number, by contrast, is known — [cuda.md](../av/cuda.md)
   §1.1).
4. **Clocking.** Egret's crystal or oscillator frequency, and whether one timebase serves the 68HC05 core
   and the seconds counter, are stated nowhere (§1.6).
5. **The one-second tick's path on the IIsi.** Three candidates, none pinned for this machine: a VIA1 CA2
   pulse (the family doc's VIA1 roster reading, [mdu.md](mdu.md) §1.3; the IIci's discrete-RTC wiring), a
   transport packet (the successor's design, [cuda.md](../av/cuda.md) §3.9), or a direct IPL0–2 drive (the
   documented Mac LC wiring [2] p. 59). The appendix's IIsi column lists no CA2 clock line, but its OCR is
   damaged, so even the negative is not certain.
6. **Auto-polling.** Whether Egret's firmware polls the ADB bus autonomously (the successor's model, with
   a host-installed device bitmap — [cuda.md](../av/cuda.md) §3.8) or only executes host-issued commands
   (the classic ROM-driven model — [ADB](../../hardware/adb.md) §"Auto-Polling (ROM-Driven)").
7. **PRAM addressing and protection.** The 256 bytes' window inside the microcontroller, the addressing
   scheme (the classic chip's 8-sector extended mode versus the successor's flat one-page map, [cuda.md](../av/cuda.md)
   §2.5), whether a management command reaches the microcontroller's own RAM and registers, and whether
   any write-protect exists ([RTC](../../hardware/rtc.md) §"Special Commands" documents the classic
   chip's).
8. **Reset state and bring-up traffic.** Egret's power-on port/enable state (§2.6), and the IIsi ROM's
   actual controller bring-up — first transaction, PRAM read path, the order the tick, autopoll and power
   functions are enabled — for which no ROM disassembly exists in this evidence set.
9. **Flash-ROM write enable.** Which board, if any, wired the scheme's flash-ROM write-enable function
   [2] p. 58 to a real part, and how the command reaches it.
10. **The wakeup time's representation.** Whether Egret stores the programmed power-up time as seconds
    against the 32-bit counter (the successor's alarm comparator, [cuda.md](../av/cuda.md) §3.9) and what
    its resolution is; the IIsi note says only that the flags are "contained in the code" [1] ch. 5.
11. **The DFAC command on the IIsi.** The LC documents the microcontroller's sound-control duty [4] ch. 12
    p. 270; whether the IIsi's firmware retains the command (and what, if anything, it would drive — the
    IIsi sound path is the ASC) is open. The successor keeps it as a legacy string [cuda.md](../av/cuda.md)
    §3.7.
12. **Monitor connected detection.** No board's wiring for the scheme's sense function [2] p. 59 is
    documented; the IIsi's video sense belongs to the RBV ([rbv.md](rbv.md) §3.5).
13. **Egret's host-timeout behaviour.** How long the controller waits for a host that never takes a
    presented byte, and what it does on timeout (drop, retry, re-present) — the host's engagement latency
    is bounded by observation (§4.3), but the controller side is unbounded in the evidence.
14. **Restart.** Whether Egret offers a command-driven reset-without-power-removal (the successor's restart
    command, [cuda.md](../av/cuda.md) §3.11), or whether the IIsi's OS restarts through the power-on path
    only.
15. **The towers' controller.** The Quadra 900/950's Caboose answers the Egret host protocol, but which
    microcontroller and firmware Apple shipped there is not established ([mcu.md](../mcu/mcu.md) §2.10,
    §7) — the relation between the two parts' firmware, if any, is part of Egret's lineage question.
